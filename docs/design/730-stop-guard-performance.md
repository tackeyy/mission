# 730: stop guard の 30 秒契約に対する負荷非依存の性能検査

`scripts/mission-stop-guard.sh` は **`stop-verdict` の呼び出しだけ**を
`MISSION_STATE_TIMEOUT`（既定 30 秒）で囲おうとする。返らなければ判定材料を
得ないまま `block` へ倒れる。

**ただし上限が掛かるとは限らない。** `_mission_state_bounded` は `timeout` が
あればそれを、無ければ `perl` の `alarm` を使い、**どちらも無ければ上限なしで
実行する**。上限は環境に依存しており、実装として保証されていない。

| 環境 | 上限 |
|---|---|
| `timeout` あり | 掛かる |
| `timeout` なし・`perl` あり | 掛かる |
| **どちらも無い** | **掛からない**（無制限） |

**本測定を行ったホストには `timeout` が無く、`perl` の分岐で動いている。**
「30 秒で囲われている」を無条件の前提にできない。

**30 秒は `stop-verdict` 1 回あたりの上限であって、hook 全体の契約ではない。**
**しかも上記のとおり、掛かるかどうかが環境に依存する。**
間の補助コマンド（`stop-guard-observe` / `mark-halt` / `cleanup-stale`）は
囲われておらず、hook 全体の所要に上限は無い。**この区別が、本文書の検査対象を
決める。**

本文書は #730 の受け入れ条件のうち、**測定と検査方式の設計**までを扱う。実装は
別 Issue へ分ける。

## hook の実行経路

`scripts/mission-stop-guard.sh` は `while` ループで、state の状態によって
呼び出し回数が変わる。

**正常系（補助コマンドが成功し、対象 state が 1 件）の回数:**

| state | CLI 呼び出し | 内訳 |
|---|---|---|
| 無し / halted | **1 回** | `stop-verdict` |
| **active / stale / lease 期限切れ** | **3 回** | `stop-verdict` → 補助コマンド → receipt 付き `stop-verdict` |

**正常系から外れると回数は増える。** 異系統レビューが、`stop-guard-observe` の
3 試行がすべて失敗した場合に 7 回、孤児 state 2 件で 5 回を実測している。
**`mark-halt` / `cleanup-stale` の失敗では 3 回のまま**であり、「補助コマンドが
失敗すれば増える」という一般化は成り立たない。

**この 2 つはこちらでは再現できていない**（4 session を作った環境でも 1 回で
終わった。再現には失敗する補助コマンドや、孤児と判定される条件を作り込む必要が
ある）。**再現手順が確定するまで、具体的な回数は引用にとどめる。**

**確実に言えるのは「回数は固定ではない」ことである。** hook は `while` ループで
あり、補助コマンドの結果に応じて回る回数が変わる。固定なのは *正常系の* 回数で
あり、検査するならその条件を明示して固定する。

`MISSION_STATE_PY` へ記録用の shim を挟み、`init` した実 state に対して hook を
通して実測した。

**30 秒の上限は各 `stop-verdict` へ個別に掛かる**（`_mission_state_bounded`）。
**間の補助コマンドは囲われていない**（`mission-stop-guard.sh:67` 付近の
`mark-halt` / `cleanup-stale` / `stop-guard-observe` は直接 `python3` を呼ぶ）。

## 測定（2026-09-03）

active state の hook を 8 回ずつ実行し、壁時間と CPU 時間（`RUSAGE_CHILDREN`）を
記録した。負荷は同ホストで `make test` を回して生成した。

| load average | hook 全体の壁時間（中央値 / 最大） | CPU 時間（中央値） |
|---|---|---|
| 1.9 | 0.893s / 0.899s | 0.880s |
| 9.8–11.6 | 1.488s / 1.587s | 1.257s |

**load が約 5 倍で壁時間の中央値は 1.67 倍。** 30 秒に対する余裕は、高負荷側の
最大値（1.587s）基準で **19 倍**。

**この 2 点だけが本測定の主張である。** 2 点では伸び方の関数形は決まらない。

### 再現手順

1. 計測対象の active state を作る。`/tmp/hooktest` で `git init -b main` し、
   `user.email` / `user.name` を設定してから、`MISSION_SESSION_ID=hooktest` を
   付けて `mission-state.py init "<mission 文字列>" --complexity Simple
   --issue-ref probe-1` を実行する（**mission 文字列は必須の位置引数**）。
2. 高負荷側のみ、同ホストで `make test`（`-n auto`）を並行して回す。
3. `MISSION_SESSION_ID=hooktest` を環境に置き、`bash scripts/mission-stop-guard.sh`
   へ `{"cwd":"/tmp/hooktest"}` を stdin で渡す試行を 8 回、間に 1 秒を置いて
   実行する。各試行で `time.monotonic()` の差と、`RUSAGE_CHILDREN` の
   `ru_utime + ru_stime` の前後差、`os.getloadavg()[0]` を記録する。

回数の測定は `MISSION_STATE_PY` に shim を置き、渡された引数をログへ追記して
から実体へ委譲する。

### 生データ

**壁時間しか保存していない。** CPU 時間と試行別 load は集計値
（中央値・範囲）だけを控えており、**試行ごとの値は残っていない**。
したがって表中の CPU 時間（0.880s / 1.257s）と比（1.43 倍）は**再計算できない**。

低負荷（load 1.93）の壁時間、8 試行（秒）:

    0.896 0.898 0.899 0.893 0.883 0.892 0.888 0.876

高負荷（load 9.8-11.6）の壁時間、8 試行（秒）:

    1.45 1.53 1.59 1.56 1.33 1.41 1.52 1.46

**高負荷側は小数第 2 位までしか控えていない。** そのため中央値 1.488s /
最大 1.587s は上の値からは再現できない（集計時のみ第 3 位まで保持していた）。

**再測定する場合は、試行ごとに壁時間・CPU 時間・load を 3 つとも保存する。**

### 測定条件と限界

- 試行 8 回、各試行の間に 1 秒
- 対象は `init` で作った active state（`/tmp` の別 repo）
- 負荷は同ホストの `make test`（`-n auto`）
- CPU 時間は親プロセスで `RUSAGE_CHILDREN` の前後差
- **load average は 1 分平均**であり、サブ秒処理の瞬間的な CPU 競合を直接は
  表さない。**負荷の唯一の指標としては不十分である**
- **試行 8 回は分布を語るには少ない。** 中央値と最大値の比較にとどめ、
  伸び方の性質は主張しない

### この測定が示していないこと

- **load 11.6 を超える領域**（本測定の最大）。2026-08-30 に観測された
  load 85 は再現していない
- **`stop-verdict` 単体と hook 全体の内訳**。3 回の呼び出しそれぞれの所要は
  分けて測っていない
- **伸び方の関数形**。2 つの load 帯しか測っておらず、線形か否かは決まらない

**Issue が引用する「load 8 → 64 で 6 倍（0.34 → 2.13 秒）」との関係は
UNKNOWN である。** 旧測定の手順と生データが無く、本測定と条件を揃えられない。
**本測定を根拠に旧測定を否定しない。**

## 検査方式

### 回数だけでは 30 秒契約を検証できない

**回数が不変でも hook 全体は 30 秒を超えうる。** 上限は各 `stop-verdict` へ
個別に掛かり、補助コマンドは囲われていない。単価が上がれば回数が同じでも
所要は伸びる。

**したがって回数検査は「30 秒契約の検証」ではない。** 検査するとすれば、
**「呼び出し回数が設計どおりであること」**という別の性質であり、そう名乗る。

### 何を検査するか（2 つに分ける）

**1. 正常系の回数（負荷非依存）**

正常系の呼び出し回数を固定する。期待値は **無し/halted で 1、active で 3**。

**これが検出するのは「正常系の fan-out が増えたこと」である。** hook に CLI
呼び出しを 1 つ足せば正常系の所要はその分伸びる。**30 秒契約の検査ではない。**

負荷に依存しないため `docs/design/516-scaling-load-independent.md` の禁止
（wall-clock を成功条件にすること）には当たらない。

**2. 単価（記録のみ、成功条件にしない）**

CPU 時間を記録する。負荷非依存に近いが完全ではない（本測定で load 5 倍に対し
1.43 倍）。キャッシュやメモリ帯域で変動するため、**失敗の判定には使わない**。

### 30 秒そのものは検証しない

**この設計は 30 秒契約を検証しない。**

検証するには `stop-verdict` 1 回が 30 秒に達する条件を再現する必要があるが、
**その条件が何かを本測定は特定していない。** 2026-08-30 の観測（load 85）は
再現しておらず、**load がその値であることが必要条件なのかも分かっていない**
（state のサイズ・I/O・ロック待ちなど、他の因子を切り分けていない）。

**「回数を固定したから 30 秒は守られる」とは書かない。** 回数は所要を構成する
2 因子の片方にすぎない。

### どこで回すか

**決まっていない。** 回数検査は shim を挟んで hook を 1 回通すだけで、実測で
0.9 秒（低負荷）/ 1.6 秒（高負荷）である。#702 が実測した 162〜299 秒の job に
対しては小さいが、**どの job へ入れるか・どの頻度で回すかは #708（シャード
偏りの是正要否）の結論に依存する**。

単価（CPU 時間）の記録先も決めていない。**記録するとだけ書いて、どこへ
どう残すかを決めていない状態である。**

**この節は未決であり、実装 Issue を切る前に決める必要がある。**

## Issue #730 の受け入れ条件との関係

**本設計は「30 秒契約そのものの検証」を満たさない。** 検査するのは正常系の
fan-out（呼び出し回数）であり、所要そのものではない。

| #730 の条件 | 本文書 |
|---|---|
| 低負荷・高負荷で所要が実測され、30 秒に対する余裕が数値で示されている | 満たす（生データ付き。測定範囲は load 11.6 まで） |
| 単価と回数を分けて記録する方式が決まっている | **満たさない**（回数は検査すると決めたが、単価の記録方法と保存先は未決。#742 が引き取る） |
| 検査の置き場所と頻度が決まっている | **満たさない**（下記） |
| 壁時間を成功条件にしていない | 満たす |
| 30 秒契約そのものを検証する | **満たさない**（timeout に至る条件が未特定。#742 が引き取る） |

**30 秒契約そのものの検証は未達である。** timeout に至る条件を特定していない
ためで、その特定は #742 が引き取る。

**置き場所と頻度も決まっていない。** 「CI の既存 job」とだけ書いて job 名を
特定しておらず、頻度も #708 と併せて後決めとしている。**後決めするものを
「決まっている」とは書けない。** 単価（CPU 時間）の記録先も未定である。

**したがって #730 の AC のうち 3 つが未達**であり、本文書だけでは Issue を
閉じられない。未達の 3 つ（単価の記録方法・置き場所と頻度・30 秒契約の検証）は
**#742 が引き取る**。

## 上限が掛からない環境の扱い（#742 へ）

`timeout` も `perl` も無い環境では上限が掛からない。**その環境で hook が
返らなければ、Stop は永久に止まる。**

本文書はこれを解かない。**測定と検査方式の設計が範囲であり、実装の保証を
変えるのは別の判断である**（Python 側で `signal.alarm` を使う、hook を
Python へ寄せる、依存を必須にする等、選択肢がある）。

**#742 へ引き取る。**

## `MISSION_STATE_TIMEOUT` の値は変えない

測定範囲（load 11.6 まで）では 19 倍の余裕がある。**変える根拠が無い。**

load 85 の事象は未確認のまま残る。**未確認を理由に値を動かすと、動かした後も
何が起きていたか分からないままになる。**

## 実装で作るもの（別 Issue）

- state の状態ごとに hook の CLI 呼び出し回数を固定するテスト（1 / 3）
- **active 経路を必ず通す。** state を持たない環境では 1 回しか回らず、
  分岐の先が検査されない
- 失敗時のメッセージに「回数を数えている」ことを書く。単価の劣化と誤読させない

## 対象外

- `MISSION_STATE_TIMEOUT` の値の変更（上記）
- hook の実装最適化（#702 / #705）
- `test_stop_hook.py` の再変更（#728 の 2 件は fallback と hang 保護の検証であり、
  目的が違う）

## この文書の初版が誤っていた点（記録）

初版は「hook 1 回あたりの CLI 呼び出しは 1 回」と書いていた。**active state を
一度も通さずに測ったためである**（worktree には `.mission-state` が無く、
mission repo の state は `halted` だった）。

**分岐の先を通さずに「固定である」と断定していた。** 異系統レビューが
active / stale の各経路を実測して 3 回であることを示し、訂正した。
