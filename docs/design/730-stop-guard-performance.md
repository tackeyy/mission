# 730: stop guard の 30 秒契約に対する負荷非依存の性能検査

`scripts/mission-stop-guard.sh` は `mission-state.py` の各呼び出しを
`MISSION_STATE_TIMEOUT`（既定 30 秒）で囲う。返らなければ判定材料を得ないまま
`block` へ倒れる。**この 30 秒が hook の契約だが、それを検証する経路が無い。**

本文書は #730 の受け入れ条件のうち、**測定と検査方式の設計**までを扱う。実装は
別 Issue へ分ける。

## hook の実行経路

`scripts/mission-stop-guard.sh` は `while` ループで、state の状態によって
呼び出し回数が変わる。

| state | CLI 呼び出し | 内訳 |
|---|---|---|
| 無し / halted | **1 回** | `stop-verdict` |
| **active** | **3 回** | `stop-verdict` → `stop-guard-observe` → receipt 付き `stop-verdict` |

`MISSION_STATE_PY` へ記録用の shim を挟み、`init` した実 state に対して hook を
通して実測した。

**30 秒の上限は各 `stop-verdict` へ個別に掛かる**（`_mission_state_bounded`）。
**間の補助コマンドは囲われていない**（`mission-stop-guard.sh:67` 付近の
`mark-halt` / `cleanup-stale` / `stop-guard-observe` は直接 `python3` を呼ぶ）。

## 測定（2026-09-03）

active state の hook を 8 回ずつ実行し、壁時間と CPU 時間（`RUSAGE_CHILDREN`）を
記録した。負荷は同ホストで `make test` を回して生成した。

| load average | hook 全体の壁時間（中央値 / 最大） | CPU 時間（中央値） |
|---|---|---|
| 1.9 | 0.893s / 0.899s | 0.880s |
| 9.8–11.6 | 1.488s / 1.587s | 1.257s |

**load が約 5 倍で壁時間は 1.67 倍。** 30 秒に対する余裕は、高負荷側の最大値基準で
**19 倍**。

### 測定条件

- 試行 8 回、各試行の間に 1 秒
- 負荷は同ホストの `make test`（`-n auto`）
- CPU 時間は親プロセスで `RUSAGE_CHILDREN` の前後差
- **load average は 1 分平均**であり、サブ秒処理の瞬間的な CPU 競合を直接は
  表さない。**負荷の唯一の指標としては不十分である**

### この測定が示していないこと

- **load 23 を超える領域**。2026-08-30 に観測された load 85 は再現していない
- **`stop-verdict` 単体と hook 全体の内訳**。3 回の呼び出しそれぞれの所要は
  分けて測っていない
- **試行ごとの分散**。中央値と最大値のみで、分布は記録していない

**Issue が引用する「load 8 → 64 で 6 倍（0.34 → 2.13 秒）」との関係は
UNKNOWN である。** 旧測定の手順と生データが無く、本測定と条件を揃えられない。
**本測定を根拠に旧測定を否定しない。**

## 検査方式

### 回数だけでは 30 秒契約を検証できない

**回数が不変でも hook 全体は 30 秒を超えうる。** 上限は各 `stop-verdict` へ
個別に掛かり、補助コマンドは囲われていない。単価が上がれば回数が同じでも
所要は伸びる。

**したがって回数検査は「30 秒契約の検証」ではない。** 検査するとすれば、
**「呼び出し回数が設計どおりであること」**という別の性質であり、そう名乗る。

### 何を検査するか（2 つに分ける）

**1. 回数の不変（負荷非依存）**

state の各状態に対する呼び出し回数を固定する。期待値は **無し/halted で 1、
active で 3**。増えれば所要はその分伸びる。

負荷に依存しないため `docs/design/516-scaling-load-independent.md` の禁止
（wall-clock を成功条件にすること）には当たらない。

**2. 単価（記録のみ、成功条件にしない）**

CPU 時間を記録する。負荷非依存に近いが完全ではない（本測定で load 5 倍に対し
1.43 倍）。キャッシュやメモリ帯域で変動するため、**失敗の判定には使わない**。

### 30 秒そのものは検証しない

**この設計は 30 秒契約を検証しない。** 検証するには、実際に timeout する負荷帯
（load 85 付近）を再現する必要があり、それは複数セッションの同時 full suite を
要する（`~/.claude/rules/github-collaboration.md` §8 が直列化を求めている）。

**「回数を固定したから 30 秒は守られる」とは書かない。** 回数は所要を構成する
2 因子の片方にすぎない。

### どこで回すか

回数検査は CI の既存 job へ入れる。shim を挟んで hook を 1 回通すだけで、
実測で 0.9 秒（低負荷）である。#702 が実測した 162〜299 秒の job に対して小さい。

**ただし「無視できる」とは書かない。** 高負荷時は 1.6 秒で、job の偏りに
影響しうる。#708（シャード偏りの是正要否）と併せて配置を決める。

## `MISSION_STATE_TIMEOUT` の値は変えない

測定範囲（load 11.6 まで）では 19 倍の余裕がある。**変える根拠が無い。**

load 85 の事象は未確認のまま残る。**未確認を理由に値を動かすと、動かした後も
何が起きていたか分からないままになる。**

## 実装で作るもの（別 Issue）

- state の状態ごとに hook の CLI 呼び出し回数を固定するテスト（1 / 3）
- **active 経路を必ず通す。** state を持たない環境では 1 回しか回らず、
  分岐の先が検査されない
- 失敗時のメッセージに「回数を数えている」ことを書く。単価の劣化と誤読させない

## 対象外

- `MISSION_STATE_TIMEOUT` の値の変更（上記）
- hook の実装最適化（#702 / #705）
- `test_stop_hook.py` の再変更（#728 の 2 件は fallback と hang 保護の検証であり、
  目的が違う）

## この文書の初版が誤っていた点（記録）

初版は「hook 1 回あたりの CLI 呼び出しは 1 回」と書いていた。**active state を
一度も通さずに測ったためである**（worktree には `.mission-state` が無く、
mission repo の state は `halted` だった）。

**分岐の先を通さずに「固定である」と断定していた。** 異系統レビューが
active / stale の各経路を実測して 3 回であることを示し、訂正した。
