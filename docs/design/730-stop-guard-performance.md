# 730: stop guard の 30 秒契約に対する負荷非依存の性能検査

`scripts/mission-stop-guard.sh` は `mission-state.py stop-verdict` を
`MISSION_STATE_TIMEOUT`（既定 30 秒）で囲い、返らなければ判定材料を得ないまま
`block` へ倒れる。**この 30 秒が hook の契約だが、それを検証する経路が無い。**

本文書は #730 の受け入れ条件のうち、**測定と検査方式の設計**までを扱う。実装は
別 Issue へ分ける。

## 測定（2026-09-03）

`stop-verdict` を 8〜10 回ずつ実行し、壁時間と CPU 時間（`RUSAGE_CHILDREN`）を
記録した。負荷は同ホストで `make test` を回して生成した。

| load average | 壁時間（中央値） | CPU 時間（中央値） | 壁/CPU | 30 秒に対する余裕 |
|---|---|---|---|---|
| 1.7 | 0.264s | 0.258s | 1.02 | **114 倍** |
| 17.9 | 0.562s | 0.395s | 1.42 | 53 倍 |
| 23.1 | 0.493s | 0.388s | 1.27 | 61 倍 |

**load が 13.6 倍になって壁時間は 1.87 倍、CPU 時間は 1.50 倍。** 最悪でも
47 倍（壁時間の最大値基準）の余裕が残る。

### hook 1 回あたりの CLI 呼び出しは 1 回

`MISSION_STATE_PY` へ記録用の shim を挟んで実測した。active state の有無に
かかわらず **`stop-verdict` の 1 回のみ**である。

```
$ echo '{"cwd":"..."}' | MISSION_STATE_PY=<shim> bash scripts/mission-stop-guard.sh
CLI 呼び出し回数: 1
   1 stop-verdict --hook-input
```

## Issue の前提のうち、測定で覆ったもの

**#730 は「負荷に対して起動コストが 2 桁のオーダーで伸びる」と述べ、
load 8 → 64 で 6 倍（0.34 → 2.13 秒）という値を根拠にしていた。**
本測定では load 13.6 倍で 1.87 倍であり、**線形を下回る**。

**#730 は「単価は #702 が測っているので、足りないのは回数のほう」とも述べていた。**
回数は 1 で固定であり、**分けて記録する対象が現時点では存在しない**。

したがって「単価と回数を分けて記録する」仕組みは、いま作っても記録する値が
片方しかない。**作るべきはそこではない。**

## load 85 の事象は説明できていない（UNKNOWN）

2026-08-30 に 2 セッションが同時に full suite を回し、load 85 で両セッションが
`mission Stop guard decision is unavailable` を観測した。

**本測定は load 23 までで、そこまでは線形以下である。** load 85 を単独で再現するには
複数セッションの同時 full suite が要り、他セッションを巻き込む
（`~/.claude/rules/github-collaboration.md` §8）。

**したがって「load 85 で何が起きたか」は未確認のまま残す。** 「線形以下だったから
85 でも大丈夫」とも「非線形に伸びるはず」とも書かない。**測っていない領域について
断定しないことが、この文書の要件である。**

## 検査方式

### 何を検査するか

**回数を検査する。** 所要 ≒ 単価 × 回数であり、

- **単価**は #702 が追跡している（起動 + import で 0.26 CPU 秒/回）
- **回数**は 1 で固定だが、**それを守っている仕組みが無い**

hook に CLI 呼び出しを 1 つ足せば所要は 2 倍になる。**単価の劣化より起きやすく、
今は誰も見ていない。**

### どう検査するか

`MISSION_STATE_PY` へ記録用の shim を挟み、hook を 1 回通して呼び出し回数を数える。
**負荷に依存しない**（回数は負荷で変わらない）。

`docs/design/516-scaling-load-independent.md` が禁じているのは
**wall-clock を成功条件にすること**であり、回数はその対象外である。

### CPU 時間を成功条件にはしない

CPU 時間は負荷非依存に近い（本測定で 1.50 倍）が、**完全ではない**。キャッシュの
効き方や他プロセスとのメモリ帯域の奪い合いで変動する。**記録はするが、失敗の
判定には使わない。**

### どこで回すか

**CI の既存 job へ入れる。** 回数を数えるだけなので数百ミリ秒で終わり、
#702 が実測した 162〜299 秒の job に対して無視できる。専用の計測基盤は要らない。

**#708（シャード偏りの是正要否）とは独立に決められる。** あちらは分単位の偏りの
話で、こちらは 1 秒未満の追加である。

## `MISSION_STATE_TIMEOUT` の値は変えない

本測定の範囲（load 23 まで）では 47 倍の余裕がある。**変える根拠が無い。**

load 85 の事象は未確認のまま残るが、**未確認を理由に値を動かすと、動かした後も
何が起きていたか分からないままになる。** 値の変更は、load 85 帯を実測してから
判断する。

## 実装で作るもの（別 Issue）

- hook を 1 回通して CLI 呼び出し回数を数えるテスト
- 期待値は 1。増えたら落ちる
- 落ちたときに「単価が上がった」と誤読されないよう、**回数を数えている**ことを
  テスト名とメッセージに書く

## 対象外

- `MISSION_STATE_TIMEOUT` の値の変更（上記）
- hook の実装最適化（#702 / #705）
- `test_stop_hook.py` の再変更（#728 の 2 件は fallback と hang 保護の検証であり、
  目的が違う）
