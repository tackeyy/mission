Refs #468 / #480（同じく負荷起因の flake だが別テスト）

# 事象

`skills/mission/tests/test_issue209_review_tier_negation.py::test_dense_no_boundary_context_analysis_scales_below_quadratic` が、**並列フルスイート実行時にのみ稀に失敗**する。単体再実行では通る。

観測（いずれもローカルの並列フルスイート）:

- 2026-08-14 #476 の検証時に 1 回
- 同日 #499 の検証時に 1 回
- いずれも `pytest -q -n auto --dist loadfile skills/mission` 実行中。同一 commit の単体再実行では pass

# 原因の見立て（未確定）

このテストは入力サイズに対する処理時間の**スケーリング**を測り、二次未満であることを assert する。並列ワーカーが CPU を奪い合う状況では実測時間が非線形に伸び、閾値を超えうる。実際、複数の worktree で同時にフルスイートを回していた時間帯に集中して発生している。

ただし「負荷のせい」と断定はしない。確認できているのは上記の観測のみで、アルゴリズムの計算量が実際に劣化していないことを独立に示せていない。

# 提案（codex 委譲可能な粒度）

1. **計測方法を wall-clock から負荷非依存の指標へ変える**のが本筋。処理時間ではなく、入力サイズに対する**操作回数**（正規表現マッチ試行数、走査したセグメント数など）を計測して二次未満を検証する。これなら CPU 競合の影響を受けず、計算量の劣化そのものを検出できる
2. それが難しい場合の次善策として、失敗時に「実測時間・入力サイズ・比率・閾値」を診断出力する（#468 / #480 と同じ方針）
3. **timeout の緩和・retry・skip は入れない**。計算量の劣化を検出するテストなので、甘くすると本来の目的を失う

# 受け入れ条件

- [ ] 並列フルスイートで安定して通る
- [ ] 計算量が実際に二次以上へ劣化した場合には失敗する（劣化を注入して確認する）
- [ ] retry / skip / 閾値の緩和を入れていない
- [ ] 既存テスト全緑

# 補足

#468（publish の inode 検証）と #480（FIFO の timeout）も負荷起因が疑われる flake だが、原因も対象も異なるため別 Issue として扱う。3 件に共通するのは「実時間や実行順序に依存する assertion」で、並列実行下で不安定になる点。

# 採用した指標と、操作回数を採らなかった理由（2026-08-30 / PR #710・Issue #703）

本文の提案 1「処理時間ではなく**操作回数**を計測する」に対し、実装は **CPU 時間**（`time.process_time`）による相対比較を採った。本節はその判断を記録する。**提案 3（timeout の緩和・retry・skip を入れない）は維持しており、実装も緩和していない。**

## 操作回数では検出できない対象があった

同ファイルには既に操作回数方式（`_counted_decision`）があり、`_actual_operation_signal_detail` の呼び出し回数を数える。これは候補が多数ある入力には有効である。

しかし `test_adversarial_long_mission_is_evaluated_without_regex_blowup` の入力は候補（`deploy`）を **1 件しか含まない**。呼び出し回数は入力長によらず常に 1 になるため、**単一の正規表現マッチ内部で起きる超線形の伸び（本テストが守っている ReDoS）を検出できない**。本文が例示する「正規表現マッチ試行数」を数えるには Python の `re` に計測点が無く、実装できなかった。

## CPU 時間が要件を満たす理由

負荷非依存という要件は CPU 時間でも満たせる。他プロセスに CPU を奪われて待たされた時間は `process_time` に計上されないため、**並列ワーカーの CPU 競合の影響を原理的に受けない**。

これは実測で確認している。壁時間の相対比（min-of-3）で実装した版は、10 並列の負荷下で **5 回中 1 回 fail した**（ratio 13.16x / limit 8x）。同じ実行で detector が `DID NOT RAISE` となり、注入した二次コストが基底コストの膨張に埋もれて**検出力まで失っていた**。CPU 時間へ切り替えた版は同条件で 5 回連続 green である。

## 閾値は緩和ではなく指標の置換である

`_SUPERLINEAR_RATIO_LIMIT = 8`（入力 4 倍で所要 8 倍未満）は、線形の約 4 倍と二次の約 16 倍の中間に置いたもの。CPU 時間・アイドルでの実測は adversarial 3.69x / repeated 4.36x / dense 3.88x で、いずれもほぼ線形であり、閾値は真値に対し約 2 倍の余裕がある。**絶対の壁時間予算（`elapsed < 2.0` 等）は削除しており、緩和ではない。**

## 検出力の実証

`test_adversarial_long_mission_detector_rejects_quadratic_cost` が、候補評価に入力長の二乗に比例する **CPU 負荷**を注入してスケーリング検査が落ちることを確認する。`sleep` では `process_time` に計上されず実証にならないため、実際に CPU を消費するループを使っている。この detector は `_actual_operation_signal_detail` を差し替えるため、同関数を経由する 3 つの検査の検出力を一括して担保する。

あわせて、基準側が計測分解能に埋もれた場合は比の判定へ進まず「入力が小さすぎて測れない」と明示して落とす（黙って通すと検査が空洞化し、黙って落とすと偽陽性になるため）。この挙動も `test_scaling_check_reports_an_unmeasurable_baseline_instead_of_failing_blindly` で固定している。

## 本文の位置づけ

本文が整理した「実時間や実行順序に依存する assertion」という類型は有効であり、#468 / #480 / #516 に加えて **#714**（stop hook の lsof timeout）が 4 件目として観測されている。
