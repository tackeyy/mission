Refs #468 / #480（同じく負荷起因の flake だが別テスト）

# 事象

`skills/mission/tests/test_issue209_review_tier_negation.py::test_dense_no_boundary_context_analysis_scales_below_quadratic` が、**並列フルスイート実行時にのみ稀に失敗**する。単体再実行では通る。

観測（いずれもローカルの並列フルスイート）:

- 2026-08-14 #476 の検証時に 1 回
- 同日 #499 の検証時に 1 回
- いずれも `pytest -q -n auto --dist loadfile skills/mission` 実行中。同一 commit の単体再実行では pass

# 原因の見立て（未確定）

このテストは入力サイズに対する処理時間の**スケーリング**を測り、二次未満であることを assert する。並列ワーカーが CPU を奪い合う状況では実測時間が非線形に伸び、閾値を超えうる。実際、複数の worktree で同時にフルスイートを回していた時間帯に集中して発生している。

ただし「負荷のせい」と断定はしない。確認できているのは上記の観測のみで、アルゴリズムの計算量が実際に劣化していないことを独立に示せていない。

# 提案（codex 委譲可能な粒度）

1. **計測方法を wall-clock から負荷非依存の指標へ変える**のが本筋。処理時間ではなく、入力サイズに対する**操作回数**（正規表現マッチ試行数、走査したセグメント数など）を計測して二次未満を検証する。これなら CPU 競合の影響を受けず、計算量の劣化そのものを検出できる
2. それが難しい場合の次善策として、失敗時に「実測時間・入力サイズ・比率・閾値」を診断出力する（#468 / #480 と同じ方針）
3. **timeout の緩和・retry・skip は入れない**。計算量の劣化を検出するテストなので、甘くすると本来の目的を失う

# 受け入れ条件

- [ ] 並列フルスイートで安定して通る
- [ ] 計算量が実際に二次以上へ劣化した場合には失敗する（劣化を注入して確認する）
- [ ] retry / skip / 閾値の緩和を入れていない
- [ ] 既存テスト全緑

# 補足

#468（publish の inode 検証）と #480（FIFO の timeout）も負荷起因が疑われる flake だが、原因も対象も異なるため別 Issue として扱う。3 件に共通するのは「実時間や実行順序に依存する assertion」で、並列実行下で不安定になる点。
