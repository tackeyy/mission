# 設計: 統合ゲートが suite の失敗行を surface する（tackeyy/mission #770）

## 目的

`gate-and-merge` が declared suite の失敗で止まったとき、**どのテストがどう落ちたかが
ログに出ない。** 出るのは終了コードだけである。

```python
if result.returncode != 0:
    if logger is not None:
        logger("suite_exit={}".format(result.returncode))
    raise IntegrationGateError(step, "suite-failed", "integrated tree suite failed")
```

`result` は stdout / stderr を捕捉しているのに使っていない。そのため、ゲートが止まっても
**本当の欠陥か環境由来かを区別できない。**

実害: #769 でゲートを 5 回実行し、手元で同じ条件を再現して初めて中身が分かった。
合計およそ 1.5 時間を失った。

## スコープ

### やること

- `run_declared_suite` が非 0 終了を報告するとき、**捕捉した出力から失敗の所在を
  logger へ出す**

### やらないこと

- ゲートの判定ロジックの変更。失敗を失敗と判定すること自体は正しい
- 成功時の出力を増やすこと
- `test_stop_guard_dedupe.py` 等が負荷依存で落ちる問題そのもの（#771 で扱う）
- suite の実行方法・並列度の変更

## 変更対象

| ファイル | 変更 |
|---|---|
| `skills/mission/lib/integration_gate.py` | `run_declared_suite` の非 0 終了時の報告 |
| `skills/mission/tests/test_issue770_gate_failure_lines.py` | 新規 |
| `plugins/mission/skills/mission/lib/integration_gate.py` | byte-identical mirror |

## インターフェース

`run_declared_suite` の signature は**変えない**。`logger` へ渡す行が増えるだけである。

抽出は純関数として切り出す。**そうしないと、抽出の挙動を検査するのに suite の実行が要る。**

```python
def suite_failure_excerpt(stdout, stderr, *, limit): ...
```

- 戻り値は `str`
- `limit` は文字数の上限

## 決定

### D1. 出すのは stdout と stderr の両方から取る

runner は任意の argv なので、失敗の所在がどちらに出るかは決められない。
**両方を対象にし、stdout を先、stderr を後の順で連結して扱う。**

### D2. 制御文字を落としてから扱う（security 境界）

**統合ツリー上の suite は任意のバイト列を出力できる。** いまは `capture_output=True` で
隔離されているので端末へ届かないが、**抜粋を logger へ渡す時点でそれが端末へ出る。**

ANSI のエスケープ列、復帰、NUL を通すと、端末の操作・クリップボードの書き換え・
**ゲート自身のログ行を装う偽装**ができる。これは本 Issue が新しく開ける経路である。

したがって **抽出より前に、次を行う。**

**残してよいのは改行（`\n`）とタブ（`\t`）だけ**とし、次をすべて取り除く。

| 範囲 | 含まれるもの |
|---|---|
| C0 `\x00`-`\x1f`（`\n` `\t` を除く） | `\x1b`（ANSI の CSI / OSC の起点）、`\r`（行の上書き）、NUL |
| `\x7f` | DEL |
| **C1 `\u0080`-`\u009f`** | **U+009B CSI・U+009D OSC・U+0085 NEL** |
| **U+2028 / U+2029** | 行区切り・段落区切り |

**C1 を落とさないと round 1 の指摘が解消しない。** UTF-8 を解釈する端末では U+009B が
CSI として働き、U+0085 は改行として扱われうる。**改行として働く文字が残ると、接頭辞を
付けた行の途中から新しい行を作れるので、接頭辞による偽装防止が成立しない。**

**除去後に行区切りとして残るのは `\n` だけである。** これが接頭辞の前提になる。

そのうえで **抜粋の各行に固定の接頭辞を付ける。** ゲート自身の出力と見分けられるようにし、
suite が `suite_exit=0` のような行を出しても偽装にならないようにする。

**redaction はしない**（下の D5）。落とすのは**制御文字だけ**である。

### D3. 抽出は「失敗を示す語」と「末尾」を**両方**出す

**suite の出力形式に依存した抽出をハードコードしない。**
`.mission/suite-contract.json` は任意の argv を宣言できるので、pytest の書式を前提にすると
他の runner で空になる。

**判定は行頭に限らない。** runner ごとに前置きが違う。

| 形 | 例 |
|---|---|
| 行頭 | `FAILED tests/...` |
| 装飾つき | `--- FAIL: TestX`、`[ERROR] ...`、`> Task :test FAILED` |
| TAP | `not ok 3 - ...` |

**「独立した語」を次のとおり定義する。** Unicode の単語境界に依存しない。

1. 制御文字を落とした行を、**ASCII の空白**（半角空白・タブ）で分割する
2. 各要素の**前後から ASCII の記号**（`` !"#$%&'()*+,-./:;<=>?@[\]^_`{|}~ ``）を取り除く
3. 残った文字列を、対象の語と**完全一致**で比べる。**大文字小文字は区別する**
4. TAP は、**隣り合う 2 要素**が上の手順で `not` と `ok` になることとする

対象の語は `FAILED` / `FAIL` / `ERROR`、および `not ok` である。

この定義で、`--- FAIL: TestX` は要素 `FAIL:` が `FAIL` になり、`[ERROR] ...` は `[ERROR]` が
`ERROR` になり、`> Task :test FAILED` は `FAILED` が一致する。

**小文字を拾わないのは、`error` が正常な説明文に現れやすいためである。**

### 過剰一致は許容する

**正常な説明文に独立した `ERROR` が現れれば一致する。** これは避けない。

理由は 2 つある。**避けようとすると runner 固有の書式に依存する**（本設計が避けたいもの）。
そして **影響が上限で頭打ちになる** — 一致行は上限の 3 分の 2 までで、残りは末尾に使われる
ので、大量一致でも末尾が失われない（D4）。

**そして、一致の有無にかかわらず末尾も併せて出す。**

- 一致行だけを出すと、**その語を含む無関係な 1 行**があるだけで末尾が出なくなる
- 末尾だけを出すと、失敗が出力の途中にある runner で所在が分からない
- **両方を、共通の上限の中で出す。重複する行は 1 回だけ出す**

順序は「一致行 → 末尾」とし、**それぞれが何であるかを見出しで区別する。**

### D4. 上限を設け、切り捨てたことを明示する

上限は既定 4000 文字とし、**一致行と末尾で共有する。**
超えたときは切り捨てた事実を出力に含める。

**一致行が上限を埋め尽くす場合でも、末尾のための枠を残す。** 一致行に上限の 3 分の 2、
末尾に 3 分の 1 を割り当て、片方が余れば他方が使う。

### D5. 秘匿情報の redaction は入れない

suite の出力には絶対パスが載りうる。**ゲートのログは logger 経由でローカルの stdout へ出る
だけで、GitHub へ自動投稿されない。** レビューで実装を読んで確認済みである
（`execute_gate_and_merge` のローカル `print`、または CLI adapter が指定した `stdout` にしか
渡らない）。

したがって本 Issue では redaction を入れない。**入れると、いま出したい失敗行まで消しうる。**

**ログを GitHub へ貼る場合の秘匿情報 precheck は、機械検証の対象外の運用規律である。**
`~/.claude/rules/safety.md` が定めており、本 Issue では受け入れ条件に含めない。
**含めると、機械で確かめられない条件が完了判定に紛れ込む。**

### D6. 既存の `suite_exit=` 行は残す

終了コードは引き続き必要である。**追加であって置き換えではない。**

## 受け入れ条件

1. suite が非 0 で終わり、出力に失敗を示す行があるとき、その行が logger へ出る
2. 複数の失敗行があるとき、**すべて**出る（上限に達しない限り）
3. **行頭に限らず**、装飾つき（`--- FAIL:` / `[ERROR]` / `> Task ... FAILED`）と
   TAP（`not ok`）の形も拾う
4. **一致行があっても末尾が出る。** 一致と末尾が見出しで区別される
5. 失敗を示す行が 1 行も無いときも末尾が出る
6. **同じ行が一致と末尾の両方に入る場合、1 回だけ出る**
7. 出力が上限を超えたとき、**切り捨てた事実が出る**
8. **一致行が多くても、末尾のための枠が残る**
9. stdout にも stderr にも失敗行があるとき、**両方**出る
10. 出力が空のとき、例外にならず「出力が無かった」ことが分かる
11. **改行とタブ以外の制御文字が logger へ渡らない。** C0・`\x7f` に加え、
    **C1（U+009B CSI・U+009D OSC・U+0085 NEL）と U+2028 / U+2029** を含む
16. **接頭辞を回避する改行が作れない。** 除去後に行区切りとして働く文字が `\n` だけである
12. **抜粋の各行に固定の接頭辞が付く。** suite が `suite_exit=0` を出力しても、
    ゲート自身の行と見分けられる
13. **suite が成功したときの logger 出力は変わらない**
14. 既存の `suite_exit=<code>` 行は引き続き出る
17. 対象の語が**独立した要素として**現れる行だけが一致する。
    語の一部（`FAILURE` の中の `FAIL` 等）では一致しない
18. 上のそれぞれについて、**壊す変異を注入して落ちることを確認する**

## テストリスト

`suite_failure_excerpt` の純関数テストを主とし、`run_declared_suite` 経由の統合テストを
少数置く。**runner は差し替え可能なので、suite を実際に回す必要は無い。**

- 純関数: 失敗行の抽出（単一・複数・stdout と stderr の両方・装飾つき・TAP）
- 純関数: 一致行があっても末尾が出ること、重複が 1 回だけになること
- 純関数: 上限超過と切り捨ての明示、一致行が多いときの末尾の枠
- 純関数: 制御文字の除去（C0・C1・DEL・行区切り）と接頭辞
- 純関数: 語境界（前後の記号を落とす・語の一部では一致しない）
- 純関数: 空入力
- 統合: 非 0 終了で失敗行が logger へ届く
- 統合: 0 終了で logger の内容が変わらない

**値は設計書に列挙しない。** 契約から導出できるのでテストコードが持つ。

## 検証コマンドの粒度

**反復中は対象テストだけを回す。**

```
cd skills/mission && python3 -m pytest tests/test_issue770_gate_failure_lines.py -q -p no:randomly
```

関連する既存テスト:

```
cd skills/mission && python3 -m pytest tests/test_issue735_suite_contract.py -q -p no:randomly
```

**`make test`（full suite）は絶対に回さない。** 同じマシンで別セッションが動いており、
同時に回すと双方の結果が壊れる。full suite は最後に CC が 1 回だけ回す。
