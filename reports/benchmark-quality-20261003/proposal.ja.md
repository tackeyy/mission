# Mission の品質を10倍へ近づける改善提案

調査日: 2026-10-03 JST。ソース: [`ed1d1c2723c55c08f06a82d6e397b164323b5b59`](https://github.com/tackeyy/mission/tree/ed1d1c2723c55c08f06a82d6e397b164323b5b59)。

## 提案の中心

**Mission の中心を「受入条件を実際に検証し、反例を発見し、修復を確認する仕組み」として強化する。最優先は、受入条件別の実検証、独立した反例探索、修復後の再検証を一つの閉ループにすること。**

目標は、複雑タスクで重大な不適合が残る割合を標準 Goal の10分の1へ近づけることとする。レビューの回数、内部スコア、記録の量ではなく、利用者が受け取る成果物が実際に変わる改善を選ぶ。

本文は上記ソース時点の初期調査と改善提案である。初期調査では製品変更・新規モデル比較・Issue/PR作成を行っていない。その後の詳細設計と実装状況は[品質改善の親Issue](https://github.com/tackeyy/mission/issues/876)に分けて記録する。以下の効果見込みは仮説であり、実証済みの倍率ではない。

## 1. 現行実装から見える改善余地

| 現状の一次根拠 | 品質への含意 | 改善方針 |
|---|---|---|
| `verification record` は caller 提供の `ok` を検査して保存する。失敗しても記録操作自体は Mission を停止しない | 検証結果の記録と、実際に検証が成功した保証は別。未検証の成果がレビュー判断に依存する | 実行結果を取得する検証アダプターと、必須受入条件の gate を加える |
| `mark-passes` はスコア・レビュー証跡・High件数・artifact等を検査するが、通常の `verification_history` 成功を必須としない | 証跡が整っていても、要求した動作の未達を機械的に止められない場合がある | 条件別の検証結果を完了判断の必須入力にする |
| Planner は observable な完了条件を表で返すが、元の要求との全件対応は説明に依存する | 計画から落ちた要求は実装・レビューの双方から落ちうる | 元要求 → 受入条件 → 実行 → 検証の対応を保存・照合する |
| Reviewer は実検証・テスト真正性確認を指示されているが、Codex は同一コンテキスト適用の fallback を持つ | 独立した評価として動くかは実行経路に依存する。同じ文脈による見逃しは仮説で、現行データでは未測定 | fresh context の検証役を実際に起動し、その実行証跡を残す |
| provenance、revision scope、claims ledger、fenced persistence は既にある | 証拠の整合・鮮度を守る土台はある。全面的な基盤の作り直しは不要 | 既存の証跡体系へ、実検証と条件別の修復履歴を接続する |

根拠: [verification command](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/skills/mission/bin/mission-state.py#L13846-L13891)、[検証記録の生成](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/skills/mission/lib/mission_kernel/evidence.py#L298-L345)、[完了gate](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/skills/mission/lib/mission_application/review.py#L430-L465)、[Planner契約](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/skills/mission-planner/SKILL.md)、[Reviewer契約](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/skills/mission-reviewer/SKILL.md)、[Codex fallback](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/skills/mission/SKILL.md#L113-L125)。

Reviewer の Step 0 には指定された検証を実行する義務が既にある。一方、主SKILLにはreviewerに実行義務がないという説明が残る。両者の説明も揃える必要があるが、「テスト実行を促す文言を追加する」だけでは足りない。必要なのは、実行・対象・結果を確認できる経路と、それを受入条件の判断に使う実装である。

## 2. 実装する改善は5つに絞る

### 優先1: 受入条件を検証可能な契約にする

開始時に、元の依頼から必須の成果、保つべき制約、依存先、検証方法を取り出す。条件には安定したIDを付け、元の依頼のどこに対応するかを残す。独立した短い確認工程で「計画に入っていない要求」「矛盾した条件」「実行できない検証」を探す。

各条件に保持する情報は、要求の根拠、期待結果、禁止副作用、検証手段、対象成果物、状態で十分。状態は少なくとも未検証・合格・不合格・阻害を区別する。単に計画の全ステップが終わっただけでは、要求の全件達成としない。条件の削除や緩和は履歴を残す。契約マニフェストの更新権限を実装側から分離し、実装側だけでは条件を緩和できないようにする。同じ実行者が保管先や権限も変えられる環境では、この強制力は成立しない。

- コード: 「APIが動く」ではなく、互換性、エラーパス、consumer、保存データまで具体化する。
- 調査・文書: 主張、出典、計算、矛盾、未確認事項を分ける。情報不足を正しく示すことが受入条件なら、それを達成として扱う。
- 主観的な品質: 決定的テストで証明したと扱わず、基準を固定した独立評価を使う。

**減らす不具合:** 要求の脱落、都合のよいスコープ縮小、依存する利用側の未確認。

**再利用:** Plannerの完了条件、plan import、claims ledger、既存のtyped kernel。新しい汎用ワークフローエンジンを作る必要はない。

### 優先2: 検証を実行して、その結果で完了を止める

検証アダプター自身が許可済みのコマンドや照合を実行し、条件ID、実行内容、終了コード、実行件数、対象の内容digest、出力digestを取得する。モデルが書いた `ok: true` は実行証跡の代わりにしない。

`mark-passes` は、必須条件に未検証・不合格が残る場合に受理しない。検証できない環境は阻害として可視化し、未達を成功へ変換しない。明示的に承認されたスコープ変更は別の記録で扱う。

既存の [suite report](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/scripts/write_suite_report.py) と [integration gate](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/skills/mission/lib/integration_gate.py#L469-L527) には、実行件数・対象index tree・完了statusを確認する部品がある。suite report自体は終了コードを保存せず、integration gate側がコマンドの終了コードを検査する。これらを共通化し、一般のMission受入条件へ接続する。

**減らす不具合:** テスト未実行、0件実行、古い結果の流用、失敗した必須検証があるままの完了。

**限界:** 実行証跡が正しくても、検証内容が不足していれば欠陥は残る。次の反例探索と組み合わせる。また、書き手が検証プログラムや証跡を自由に改変できる環境では完全な独立性はない。評価器・receiptの保存先を実行者から分離する。

### 優先3: 独立した検証役に反例を作らせる

検証役には、元の要件、現在の成果物、関連する実装・仕様を渡す。実装者の「正しいはず」という説明や既存の採点を先に渡さず、自分で判断させる。CC/Codexとも、fresh contextで起動した事実をruntimeの記録で確認する。同一コンテキストのfallbackは `independent=false` と記録し、独立検証が必須の条件を完了扱いにしない。

仕事は「4項目に点を付ける」だけではない。次のような具体的な反例を作り、実行・再計算する。

- 変更したAPIを別consumerから呼ぶ。部分失敗、再実行、境界値、並行実行を試す。
- 必須の検査を消す・条件を反転する等の限定的な故障を隔離環境で入れ、検証がその不具合を検出するかを見る。
- 文書の集計値を原データから再計算し、反対の結論を支持する資料、古い出典、欠けた前提を探す。
- 比較対象・費用・権限等の前提が途中で変わっていないか照合する。

異なるモデルは選択肢だが、まず異なる証拠と検証経路を持たせる。モデル名が違うだけで独立性を保証したと扱わない。

**減らす不具合:** 実装者が想定しなかった入力、実装とテストが同じ誤解を持つケース、根拠の循環。

**制約:** 全コードへの一律mutationは行わない。重要な受入条件と現実的な故障に限定し、同値mutationを欠陥と誤認しない。問題がない対照例も使い、誤検知による改悪を測る。

### 優先4: 発見から修復完了まで追跡する

反例を「指摘として書いた」で終えない。受入条件IDと結び、再現入力・失敗結果・最小修正・同じ反例の再実行・関連consumerの回帰確認まで一続きにする。

修正が入ったら、既存のrevision scope/provenance検証へ新しい検証receiptを接続する。HEADだけでなく未コミット差分・生成物も含む実際の候補内容へ束縛する。これは候補snapshotの取得規則を新設する提案であり、既存suite reportの `git write-tree` はindexを記録し、未ステージの差分まで含むものではない。依存関係が不明なら必要な検証を広めに再実行する。最終候補を固定した後、cleanな環境で重要な受入経路を確認する。

既存の [scoring provenance](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/skills/mission/lib/scoring_provenance.py)、[revision scope検証](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/skills/mission/bin/mission-state.py#L10479-L10523)、[scratch integration tree](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/skills/mission/lib/integration_gate.py#L908-L971) を再利用する。「既存の証跡鮮度検証がない」という提案ではない。

**減らす不具合:** 指摘の取り下げだけでの解決扱い、修正による別の回帰、手元環境だけでの成功。

### 優先5: 修復と最終検証に予算を残す

レビュー前に予算を消費し尽くすと品質改善は起きない。計画・初回実装・反例探索・修復・最終検証に使う予算を観測し、修復と最終検証の枠を残す。

初期の実験値として、計画10%、実装40%、検証20%、修復20%、最終検証10%を試せる。ただし、これは未検証の開始値であり、固定ルールとして採用しない。検出できた重要欠陥数、修復成功率、回帰率、時間から配分を更新する。

レビューを追加するのは、未検証の重要条件や再現可能な反例が残るとき。新しい証拠が増えない同じ議論を繰り返さず、品質改善が止まった場合は理由を明示する。予算を増やしただけの品質改善と、同予算での改善を分けて測る。

## 3. 10倍を狙う因果モデル

まず「初回に残った欠陥を何割取り除けたか」を測る。品質が上がらない原因を、モデル性能という一語にまとめない。

- `d`: 不適合な成果物を不適合と検出する割合
- `r`: 検出した成果物を、受入可能な状態まで正しく修復する割合
- `u`: 良かった成果を修正で不適合にする割合
- `p`: 重大な不適合を含む成果の割合

単純化した1回の改善モデルは `p_next = p × (1 − d×r) + (1 − p) × u`。

**数値は実測ではなく、設計目標を説明する仮定。** 初回の不適合率20%、各回で不適合な成果物の80%を検出し、その90%を受入可能な状態へ修復、正常成果を壊す率0.1%なら、1回後5.68%、2回後1.685%となり、約11.9倍の減少になる。

ここで2回目の80%は、**1回目で残った難しい不適合に対する条件付き検出率**である。同じレビューを繰り返せば成立する、という仮定ではない。機械検証と反例探索など、違う失敗を見つける工程が必要になる。

開発時は初回成果・反例探索後・修復後・最終成果を保存し、`d/r/u` と予算未達を別々に測る。10倍へ届かないとき、検出不足なのか、修復不足なのか、修正による回帰なのかが分かる。

## 4. 最初の開発実験

**最初に実装するのは、優先1・2の最小版と、優先3・4を1巡つなぐ細い実行経路。** すべての文書・全task種別に広げる前に、結果を実行で判定できるコードタスクで確かめる。

1. 開発用の複雑タスクを12件用意する。別プロジェクトの複数モジュール変更、互換性、再実行、集計整合等を対象にする。Mission自身を直す課題に偏らせない。
2. 正解・検証器を実行側から隔離する。既存の「欠陥候補一覧を与えて照合する」fixtureは回帰検知に残し、新しい発見能力の主評価にはしない。
3. 同じ初回成果から、現行Mission、実検証gate追加、反例探索と修復追加を比較する。これは修復機構を評価する診断実験で、標準Goalとの製品比較とは分ける。
4. 欠陥を含む成果に加え、正しい成果も混ぜる。未完了と報告するだけで品質が上がった扱いにせず、実際に修復できた割合・誤修正・予算内完遂を測る。
5. 有効だった改善だけを固定し、新しい未使用タスクで native Goal 対 改善後Mission を最初から最後まで比較する。

段階3で改善が出なければ、大規模ベンチマークへ進めない。結果に応じて、検証器の不足、独立性、修復手順、予算配分の該当箇所だけを直す。

## 5. ベンチマークを改善開発へどう使うか

### 比較対象

| ホスト | 基準 | 比較 |
|---|---|---|
| Claude Code | 公式 `/goal` と十分に具体的な達成条件 | 同じ要件を渡した改善後Mission |
| Codex | native Goal | 同じ要件を渡した改善後Mission |

ホストごとに結論を出す。同一ホスト内で主モデル・版・reasoning・開始snapshot・利用可能なツール・権限・総予算を合わせる。Goal側にレビューやテストを禁止しない。両側が利用できるskill/providerも揃え、Missionだけに非公開専門知識を与えない。

標準設定の製品比較では、Missionの子モデル配分も製品構成の一部として全件記録する。追加モデルや計算量による効果を分ける診断実験では、同じモデル集合・総予算を使うGoal＋独立レビューも比較する。

CCの公式Goalにも独立した完了評価器があり、Codex Goalにも永続目標と継続・完了確認がある。したがって「Goalには確認工程がない」という前提で差別化しない。差を作るのは、要求に結び付いた実検証と具体的反例の修復である。[CC公式仕様](https://code.claude.com/docs/en/goal)、[Codex公式仕様](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)。

### タスク群

| 群 | 現実的な課題 | 独立した評価 |
|---|---|---|
| 複数モジュール変更 | API・CLI・設定・生成物をまたぐ機能 | hidden consumer / integration tests |
| 互換性・データ整合 | schema変更、旧データ、部分移行 | round-trip、再実行、失敗時データ保持 |
| 指摘修復・回帰 | 局所修正と同型箇所の修正 | hidden sibling defect と統合テスト |
| 中断・再開 | agent作業の途中中断と成果の引継ぎ | 未完事項保持、二重処理・欠損・誤完了の有無 |
| 制約・権限 | 許可範囲内の変更と禁止副作用 | allowed/denied双方と副作用の実測 |
| 調査・文書 | 矛盾する資料、数値、欠けた一次情報 | 再計算、出典照合、独立した基準付き評価 |

agentの中断耐性と、作成するソフトウェアのcrash耐性は別の試験として記録する。stress課題の成功を、自然な複雑タスク全体の成功率として一般化しない。自然な依頼から選ぶ群と、特定の失敗を狙う群を別々に報告する。

### 測定する結果

- 主結果: **予算内に受入可能な成果を残せない率**。必須要件未達、重大欠陥、禁止副作用、成果なしを含む。正しいhaltが要求される課題は、そのhalt自体を受入条件にする。
- 品質の内訳: 残存欠陥、要求脱落、誤った主張、修復による回帰、根拠不足、誤完了宣言。
- 改善機構: 検出率、修復成功率、誤検知率、修正で新たに壊した率。
- コスト: 全実行・全子モデル・再試行を含むtokens、API相当費用、実時間。課金額と推定費用を混同しない。

結果は外部検証器と、必要な場合は条件名を隠した独立評価者が判断する。Missionの `passes` や内部スコアを外部品質の正解にしない。名前を隠しても出力形式から方式が推測される可能性は残るので、盲検の限界も記録する。

## 6. 実証前に整える既存ハーネス

1. **native Goalを実際に使う。** 現行Codex runnerは `codex exec` に独自のgoal-only文面を渡している。[実装](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/benchmarks/mission-vs-goal/run_paired_pilot.py#L226-L267)。Codexの [thread/goal API](https://learn.chatgpt.com/docs/app-server#manage-a-thread-goal) 等を使うアダプターを作り、設定・継続・終了のイベントを観測する。CCは公式 `/goal` を呼んでいるが、先頭の条件はartifactと見出し存在が中心なので、実際の受入条件に合わせる。[実装](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/benchmarks/mission-vs-goal/run_claude_goal_vs_mission.py#L394-L410)。
2. **固定した版を実行する。** local-authoring syncはmainを最新化し、detachedを拒否する。実験には固定SHAから作る変更不能な配布パッケージとdigest記録が必要。通常のfreshness guardを迂回する変更は行わず、配布経路として仕様化する。[sync実装](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/scripts/mission-local-authoring-sync.sh)、[配布仕様](https://github.com/tackeyy/mission/blob/ed1d1c2723c55c08f06a82d6e397b164323b5b59/docs/DISTRIBUTION.md)。
3. **評価器を隔離・固定する。** answer key、hidden tests、採点プログラムをworkerのread/write範囲外に置く。候補・出典・評価器のdigestを結果に束縛する。実行後に採点器を直した場合は再採点と明記し、確認実験には新しいデータを使う。
4. **全割当を残す。** timeout、予算切れ、Mission未起動、権限低下も記録する。製品の失敗を主結果から除外しない。外部障害の再実行は事前規則で両側対称に行い、元試行を保持する。権限が揃わない状態で性能比較を続けない。
5. **主張を事前に固定する。** 開発セットで改善を選んだ後、未使用セット・品質定義・予算・統計方法・停止規則を固定する。反復試行を独立した新規タスクとして数えない。

## 8. 実証の規模と主張の境界

最初のpilotは、例えば12タスク×2ホスト×2方式×3反復=144実行。これは機構と費用を測る開発用の規模で、10倍を証明できる標本数という意味ではない。native機能の観測だけを確認する少数の試運転を先に行う。

確認実験の件数はpilotで観測した不適合率とタスク間のばらつきから決める。同一task・同一template・同一repo由来の相関を考慮する。主解析は独立task-family単位とし、反復はfamily内として扱う。最大件数と中止条件を先に定め、良い結果が出た時点だけで止めない。

仮の例として、100件でGoal20件失敗・Mission2件失敗なら観測倍率は10倍でも、不確かさが大きい。100件でMission0件でも、独立な同一分布の二項試行を仮定した片側95%上限は約2.95%。真の失敗率がゼロとは言えない。[二項比率の正確な区間](https://itl.nist.gov/div898/software/dataplot/refman2/auxillar/exacbici.htm)。

添付の `statistical-examples.json` は、2ホスト分の4つの限界にBonferroni補正した保守的な例示計算を含む。実際の反復・階層構造へそのまま適用する手法ではない。例えば独立な300件で60対0なら、この方法でも率比上限は約0.096。実際の必要件数は未確定。

公開時の表現は結果に合わせる。両ホストの率比の信頼上限が0.1以下なら、対象タスク群・モデル・予算を付けて「受入可能な成果を残せない率が標準Goalの10分の1以下」とする。一方のホストだけならそのホストに限定する。10倍未達でも改善量と失敗例を公開し、別指標への変更で10倍を作らない。

## 推奨する着手順

**受入条件と実検証の最小gate → 独立した反例探索 → 修復と再検証 → 予算配分の調整 → 未使用タスクで比較。**

最初の実装単位は「指定した必須受入条件に、実際にその候補で成功した検証receiptがなければ完了できない」こと。その次に、既存テストが見逃す反例を見つけて修復できるかを測る。この順なら、どの改善が成果物を良くしたかを追いながら10倍を目指せる。
